## 1. The Strategy of Capstone Team Formation
  
  In standard academic courses, group projects typically span a few weeks, meaning students can survive poor team dynamics through last-minute heroics. In a two-semester capstone sequence spanning eight months, team failure is the primary cause of project collapse.
  
  The week 02 process moves students away from two common, failure-prone formation methods:
  1. **The Friendship Trap:** Forming teams exclusively based on existing social circles. Friends often share identical technical skill sets, avoid holding each other accountable for missed deadlines, and hesitate to surface constructive criticism during design reviews.
  2. **Random Assignment:** Grouping students without evaluating skill compatibility, schedule alignment, or shared grade expectations.
  
  The structured workshop protocol presented in the slides is designed to assemble **complementary, cross-functional engineering units** capable of delivering a complex system.
  
  ```
  +-------------------------------------------------------------------------+
  |                  THE COMPLEMENTARY SKILL PROFILE                        |
  +-------------------------------------------------------------------------+
  | POOR TEAM BALANCE (Redundant):                                          |
  | [ Dev 1: C++ ] + [ Dev 2: C++ ] + [ Dev 3: C++ ] + [ Dev 4: C++ ]       |
  | Result: No UI expertise, no DevOps, no DB design, high internal friction|
  |                                                                         |
  | STRONG TEAM BALANCE (Cross-Functional / T-Shaped):                      |
  | • Systems / Backend: Low-level C++, networking, data serialization     |
  | • Infrastructure / PM: Linux, containerization, Git workflows, planning |
  | • Frontend / UI: Web technologies, state management, usability          |
  | • Architecture / DB: Relational schemas, API contracts, system modeling |
  | • QA / Verification: Automated testing, test plans, edge-case detection |
  +-------------------------------------------------------------------------+
  ```

## 2. The 70-Minute Team Identification Protocol
  
  The curriculum outlines a timed, phased workshop designed to surface technical capabilities and interpersonal working styles rapidly.
  
  ```
  +-------------------------------------------------------------------------+
  |                 TEAM IDENTIFICATION TIMELINE (70 MIN)                   |
  +------------+-----------------------------------+------------------------+
  | Time       | Activity                          | Core Objective         |
  +------------+-----------------------------------+------------------------+
  | 0–5 min    | Why Team Formation Matters        | Align expectations     |
  | 5–15 min   | Engineering Identity / Skill Card | Objective self-audit   |
  | 15–35 min  | Engineering Speed Networking      | Broad candidate search |
  | 35–55 min  | Mini Team Challenge               | Pressure test dynamics |
  | 55–65 min  | Compatibility Conversations       | Working style audit    |
  | 65–70 min  | Individual Exit Ticket            | Confidential matching  |
  +------------+-----------------------------------+------------------------+
  ```
### Phase 1: Expectations and Room Mechanics (0–5 min)
  The classroom is partitioned to identify structural gaps immediately:
  * **Left Side of Room:** Incomplete groups that have an idea or partial roster but lack specific technical roles (e.g., three backend programmers seeking a frontend engineer).
  * **Right Side of Room:** Unaffiliated individuals seeking teams based on domain interest or technical alignment.
  * **Operational Directive:** Students are forced out of comfort zones to avoid clustering with familiar peers.
### Phase 2: The Engineering Identity and Skill Card (5–15 min)
  Engineers fill out a structured capability audit. In professional software development, this is known as defining a **T-Shaped Profile**: broad knowledge across the software stack combined with deep technical specialization in one or two domains.
  
  ```
  +-------------------------------------------------------------------------+
  |                     ENGINEERING SKILL CARD AUDIT                        |
  +-------------------------------------------------------------------------+
  | 1. Primary Specialization (Vertical Bar of the "T"):                     |
  |    • Systems programming (C, C++, Rust, OS drivers, memory management)  |
  |    • Backend & Data (Python, Go, Java, PostgreSQL, REST/WebSockets)     |
  |    • Client / UI (React, Svelte, Vue, TypeScript, Electron, Qt)         |
  |    • Networking & Infrastructure (Docker, CI/CD, WebRTC, Linux admin)   |
  |                                                                         |
  | 2. Secondary Capabilities (Horizontal Bar of the "T"):                  |
  |    • Familiarity with Git branching, unit testing suites, shell scripting|
  |                                                                         |
  | 3. Operational Interest:                                                |
  |    • Leadership preference: Project Management, System Architecture,    |
  |      Requirements/Product Ownership, or Quality Assurance               |
  |                                                                         |
  | 4. Project Domain Interests:                                            |
  |    • Real-time systems, gaming, robotics, AI/ML, web applications      |
  +-------------------------------------------------------------------------+
  ```
### Phase 3: Engineering Speed Networking (15–35 min)
  Students conduct short, 3- to 4-minute technical interviews with peers across the room. The objective is not social conversation, but discovering functional capability matches:
  * What technical stack have you used in prior coursework or internships?
  * Which specific role do you want to own (e.g., testing lead, backend lead)?
  * What is your daily development environment (Linux, Windows, macOS)?
### Phase 4: The Mini Team Challenge (35–55 min)
  Temporary 4- to 5-person groups are given a rapid, ambiguous engineering problem to solve in 20 minutes (e.g., sketching a high-level architecture for a real-time tracking application).
  
  * **Why this matters:** Technical skill on paper does not reveal how an engineer behaves during collaboration. The mini challenge exposes operational red flags early:
  * *The Monopolizer:* An individual who talks over everyone and dismisses alternate designs.
  * *The Passive Passenger:* An individual who disengages and contributes nothing unless directly commanded.
  * *The Pragmatic Collaborator:* An individual who listens, clarifies requirements, suggests concrete compromises, and tracks the time limit.
### Phase 5: Team Compatibility Conversations (55–65 min)
  Before finalizing a roster, potential teammates must address non-technical working habits. These differences cause severe team breakdown later in the semester if left unexamined.
  
  ```
  +-------------------------------------------------------------------------+
  |                  TEAM COMPATIBILITY CHECKLIST                           |
  +----------------------+--------------------------------------------------+
  | Evaluation Factor    | Critical Alignment Questions                     |
  +----------------------+--------------------------------------------------+
  | Ambition & Goals     | Is everyone aiming for an 'A', or are some       |
  |                      | members satisfied with just passing the course?  |
  +----------------------+--------------------------------------------------+
  | Time Commitment      | How many hours per week outside class can you    |
  |                      | commit (5 hours vs. 20 hours)?                   |
  +----------------------+--------------------------------------------------+
  | Working Cadence      | Do you work in steady, daily increments, or do   |
  |                      | you pull all-nighters before deadlines?          |
  +----------------------+--------------------------------------------------+
  | Schedule Overlap     | Are there at least two common 2-hour blocks      |
  |                      | during the week where the entire team can meet?  |
  +----------------------+--------------------------------------------------+
  | Communication Style  | Do you respond to chat messages within hours,    |
  |                      | or do you disappear for days at a time?          |
  +----------------------+--------------------------------------------------+
  ```
### Phase 6: Exit Ticket and Matching (65–70 min)
  Students submit confidential rankings of preferred teammates and project themes to the instructor. This allows the course coordinator to intervene if an individual is isolated, if a team has critical skill gaps, or if incompatible working styles are detected.

## 3. Measurable Outcomes for Week 02
  
  By the conclusion of Week 02, the team must transition from loose association to a recognized entity within the course management system:
  
  ```
  +-------------------------------------------------------------------------+
  |                        WEEK 02 EXIT DELIVERABLES                        |
  +-------------------------------------------------------------------------+
  | 1. Team Name: Formal identity established.                              |
  | 2. Confirmed Roster: 5 to 6 members with assigned functional roles.    |
  | 3. Tentative Project Title: Clear, concise application concept.         |
  | 4. Canvas Group Registration: Team workspace configured online.         |
  | 5. First Formal Team Meeting Scheduled: Meeting time, location, and     |
  |    written agenda set before leaving the classroom.                     |
  +-------------------------------------------------------------------------+
  ```
