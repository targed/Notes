### **2.4 The Domain Name System (DNS)**
#### **The Problem of Identifiers**
  
  On the internet, hosts have two primary identifiers:
  1.  **IP Address:** A numerical address (e.g., `128.119.40.186`) used by routers and the network core to forward datagrams. It's efficient for machines but difficult for humans to remember.
  2.  **Hostname:** A human-friendly, mnemonic name (e.g., `gaia.cs.umass.edu`) used in applications.
  
  The fundamental problem is how to map between these two identifiers. This is the core function of the **Domain Name System (DNS)**.
#### **DNS as an Application-Layer Service**
  
  DNS is a core internet function, but it is implemented as an **application-layer protocol**. This is a key design choice that reflects the internet's philosophy of keeping the network core simple and pushing complexity to the network's edge.
  
  *   **How it Works:** DNS uses client-server communication. The DNS servers are hosts that run at the edge of the network, and they communicate using an application-layer protocol built on top of the transport layer (typically **UDP** on port 53).
#### **Primary DNS Services**
  
  DNS is a massive, distributed database that provides several key services:
  
  1.  **Hostname-to-IP-address Translation:** This is its main job. When a user types a URL like `www.google.com` into their browser, DNS is responsible for translating that name into the corresponding IP address.
  2.  **Host Aliasing:** A single host can have multiple names. DNS can map a simple, memorable **alias name** to the more complex **canonical name** of the host.
  3.  **Mail Server Aliasing:** DNS is used to find the mail server associated with a domain (e.g., finding the server for `@gmail.com`).
  4.  **Load Distribution:** For very popular services (like major websites), a single hostname can be associated with a set of multiple IP addresses, each corresponding to a different replicated server. When a client makes a DNS query, the DNS server can rotate through this set of IP addresses, distributing the client load across the various servers.
#### **Why DNS is a Distributed System**
  
  A single, centralized DNS server would be a disastrous design for several reasons:
  *   **Single Point of Failure:** If that one server went down, the entire internet would become unusable.
  *   **Traffic Volume:** A single server would have to handle trillions of queries per day, an impossible traffic load.
  *   **Distant Centralized Database:** Users far away from the server would experience significant delays for every query.
  *   **Maintenance:** A single, massive database would be a nightmare to manage and update.
  
  For these reasons, the DNS is designed as a **distributed, hierarchical database**. It simply **does not scale** as a centralized system.
#### **The Hierarchy of DNS Servers**
  
  The DNS database is distributed among a hierarchy of name servers.
  
  1.  **Root DNS Servers:**
    *   There are 13 logical root servers worldwide, managed by various organizations. These 13 servers are heavily replicated into hundreds of physical servers for redundancy and performance.
    *   Their job is not to know every hostname but to know where to find the servers for the next level down: the TLD servers. They are the "contact of last resort."
  2.  **Top-Level Domain (TLD) Servers:**
    *   These servers are responsible for all names within a top-level domain, such as `.com`, `.org`, `.edu`, and all country-code TLDs (e.g., `.uk`, `.ca`, `.fr`).
    *   For example, the `.com` TLD server knows the location of the authoritative server for every `.com` domain.
  3.  **Authoritative DNS Servers:**
    *   Every organization with a public presence on the internet must provide its own authoritative DNS server(s).
    *   This server holds the definitive DNS **Resource Records (RR)** that map the organization's hostnames to their IP addresses (e.g., mapping `www.amazon.com` to its IP).
#### **Local DNS Servers**
  
  While not part of the formal hierarchy, the **local DNS server** is crucial to how DNS works from a user's perspective.
  *   When a host makes a DNS query, it is first sent to its local DNS server, which is typically provided by the user's ISP or institution.
  *   This local server acts as a proxy, forwarding the request into the DNS hierarchy to resolve the name on the host's behalf.
  *   Local DNS servers also heavily use **caching** to improve performance.
#### **DNS Resolution: Iterated and Recursive Queries**
  
  There are two main ways a name can be resolved:
  
  1.  **Iterated Query (Common Practice):**
    *   The requesting host sends the query to its local DNS server.
    *   The local server asks a root server. The root server replies, "I don't know the answer, but here is the IP of the TLD server you should ask."
    *   The local server then asks the TLD server. The TLD server replies, "I don't know the answer, but here is the IP of the authoritative server for that domain."
    *   The local server then asks the authoritative server, which provides the final IP address.
    *   This process involves a "conversation" between the local server and the other servers in the hierarchy.
  
  2.  **Recursive Query:**
    *   The requesting host sends the query to its local DNS server.
    *   The local server sends the query to a root server.
    *   The root server then takes on the burden of finding the answer by querying the TLD server, which in turn queries the authoritative server.
    *   The final answer is passed all the way back up the chain.
    *   This approach is not widely used in the public internet because it places a heavy processing burden on the upper levels of the hierarchy.
#### **DNS Caching**
  
  To optimize performance and reduce query traffic, caching is used extensively.
  *   **Mechanism:** When any DNS server receives a mapping, it stores (caches) that mapping locally.
  *   If another query for the same hostname arrives, the server can immediately return the cached result without needing to query other servers.
  *   **Time-to-Live (TTL):** Cached entries are not permanent. Each DNS record has a TTL value that specifies how long it can be cached. After the TTL expires, the entry is removed. This means there's a possibility of cached DNS information being out-of-date, but DNS accepts this for the massive performance benefits it provides.
#### **DNS Records and Messages**
  
  *   **DNS Resource Records (RR):** The database records stored by DNS servers. The format is a tuple: `(name, value, type, ttl)`.
    *   **Type A:** An address record mapping a hostname (`name`) to an IPv4 address (`value`).
    *   **Type NS:** A name server record mapping a domain (`name`) to the hostname of its authoritative DNS server (`value`).
    *   **Type CNAME:** A canonical name record mapping an alias (`name`) to the real hostname (`value`).
    *   **Type MX:** A mail exchange record mapping a domain (`name`) to the hostname of its mail server (`value`).
  *   **DNS Protocol Messages:**
    *   DNS queries and replies use the same message format.
    *   The message header contains an identification number to match queries with replies, and flags to specify details of the query/reply.
    *   The rest of the message is divided into sections for questions, answers, authority information, and additional helpful info.
