### **2.2.1 Web and HTTP**
#### **Overview of Web Terminology**
  
  *   **Web Page:** A document that consists of a collection of **objects**.
  *   **Object:** A file that can be addressed by a URL. This includes:
    *   A base **HTML file**, which contains the structure and text of the page.
    *   Referenced objects like JPEG images, Java applets, audio files, etc., which are linked within the base HTML file.
  *   **URL (Uniform Resource Locator):** The address used to locate an object on the web. It has two main parts:
    1.  **Host Name:** Identifies the server where the object is stored (e.g., `www.someschool.edu`).
    2.  **Path Name:** Specifies the location of the object on that server (e.g., `/someDepartment/pic.gif`).
#### **HTTP: Hypertext Transfer Protocol**
  
  *   **Definition:** HTTP is the application-layer protocol for the World Wide Web.
  *   **Architecture:** It follows the **client-server model**:
    *   **Client:** A web browser (e.g., Firefox, Safari, Chrome) that requests, receives, and displays web objects.
    *   **Server:** A web server (e.g., Apache, Nginx) that stores web objects and sends them in response to client requests.
  *   **Underlying Transport Protocol:** HTTP uses **TCP** for its transport service. This means it relies on TCP's reliable data transfer.
    *   The client initiates a TCP connection to the server, typically on **port 80**.
    *   The server accepts the TCP connection from the client.
    *   HTTP messages (requests and responses) are exchanged over this connection.
    *   Finally, the TCP connection is closed.
  
  *   **HTTP is "Stateless"**
    *   A critical characteristic of HTTP is that the server **maintains no information about past client requests**. Each request is treated independently.
    *   **Advantage:** This greatly simplifies server design. The server doesn't need to manage complex state information for millions of clients. If a client or server crashes mid-transaction, there's no state to clean up or reconcile.
    *   **Disadvantage:** Some applications *require* state (e.g., to remember items in a shopping cart). This is handled using a mechanism called **cookies**, which will be discussed later.
#### **HTTP Connection Types**
  
  There are two primary ways HTTP manages TCP connections:
  
  1.  **Non-persistent HTTP:** One TCP connection is used for each object.
  2.  **Persistent HTTP:** Multiple objects can be sent over a single, persistent TCP connection.
  
  **1. Non-persistent HTTP**
  This was the method used in the original HTTP/1.0. It is inefficient but simple to understand.
  
  *   **Process:** To download a web page with multiple objects (e.g., 1 base HTML file + 10 images):
    1.  A TCP connection is opened to the server.
    2.  The client sends an HTTP request for the base HTML file.
    3.  The server sends the HTTP response containing the HTML file.
    4.  The server closes the TCP connection.
    5.  The client receives and parses the HTML file, discovering the 10 referenced images.
    6.  **Steps 1-4 are repeated for each of the 10 images.** This means a total of **11 separate TCP connections** are established and torn down.
  
  *   **Response Time Analysis:**
    *   Let **RTT (Round-Trip Time)** be the time it takes for a small packet to travel from the client to the server and back.
    *   To get a single object, the total response time is the sum of:
        *   **1 RTT** to initiate the TCP connection (the handshake).
        *   **1 RTT** for the HTTP request to travel to the server and the first few bytes of the response to return.
        *   The time it takes to transmit the entire file.
    *   **Equation for Non-persistent HTTP Response Time (per object):**
        $ \text{Response Time} \approx 2 \cdot \text{RTT} + \text{File Transmission Time} $
  *   **Issues with Non-persistent HTTP:**
    *   It's slow, requiring **2 RTTs of overhead for every single object**.
    *   It creates significant overhead on the server, which must manage system resources (buffers, variables) for each new connection.
  
  **2. Persistent HTTP (HTTP/1.1 and later)**
  This is the default and much more efficient method used today.
  
  *   **Process:**
    1.  The client opens a single TCP connection to the server.
    2.  It sends requests for multiple objects over that same connection.
    3.  The server sends the responses for those objects over the same connection.
    4.  The connection is left open for a period of time (e.g., on a timer) and is only closed after a timeout or by an explicit request.
  *   **Advantages:**
    *   Eliminates the TCP connection setup overhead for every object after the first one.
    *   Cuts the response time nearly in half, reducing the per-object latency from 2 RTTs to **1 RTT**.
    *   Reduces the resource burden on the web server.
#### **HTTP Messages**
  
  HTTP communication involves two types of messages, both written in human-readable ASCII text.
  
  **1. HTTP Request Message**
  Sent from the client to the server.
  *   **General Format:**
    1.  **Request Line:** Specifies the method, the URL of the object, and the HTTP version.
    2.  **Header Lines:** A series of lines providing additional information, such as the host, browser type (`User-Agent`), and connection type (`Connection: keep-alive`).
    3.  A blank line.
    4.  **Entity Body:** An optional body, used for methods like `POST` to send form data to the server.
  
  *   **Common Request Methods:**
    *   **`GET`:** The most common method. Requests an object. All data is sent in the URL line itself.
    *   **`POST`:** Used to submit form data. The data is included in the entity body of the message.
    *   **`HEAD`:** Asks the server to send just the headers, without the actual object. Useful for debugging or checking when an object was last modified.
    *   **`PUT`:** Uploads a file to a specified path on the server.
  
  **2. HTTP Response Message**
  Sent from the server to the client.
  *   **General Format:**
    1.  **Status Line:** Specifies the HTTP version, a **status code**, and a human-readable **status phrase**.
    2.  **Header Lines:** Includes information like the date, server type, when the object was last modified (`Last-Modified`), and the object's size (`Content-Length`).
    3.  A blank line.
    4.  **Entity Body:** The actual requested object (e.g., the HTML file, the image).
  
  *   **Common Response Status Codes:**
    *   **`200 OK`:** The request was successful, and the object is included in the response.
    *   **`301 Moved Permanently`:** The requested object has moved. The new location is given in the `Location:` header.
    *   **`400 Bad Request`:** The request was malformed and the server could not understand it.
    *   **`404 Not Found`:** The requested object does not exist on this server.
    *   **`505 HTTP Version Not Supported`:** The server does not support the version of HTTP requested by the client.
#### **Maintaining User State with Cookies**
  
  Since HTTP is stateless, cookies were invented to allow websites to recognize users and maintain some state across multiple transactions.
  
  *   **What Cookies Are For:**
    *   Authorization (keeping you logged in).
    *   Managing shopping carts.
    *   Providing personalized recommendations.
    *   Tracking user session state.
  *   **The Four Components of Cookies:**
    1.  A **cookie header line** in the HTTP response message from the server (e.g., `Set-Cookie: 1678`).
    2.  A **cookie header line** in subsequent HTTP request messages from the client (e.g., `Cookie: 1678`).
    3.  A **cookie file** kept on the user's local machine, managed by the browser, which stores cookies for different websites.
    4.  A **back-end database** on the website, which links cookie IDs to user-specific information.
  
  *   **How Cookies Work (Example):**
    1.  A user visits Amazon for the first time.
    2.  The Amazon server creates a unique ID for the user (e.g., `1678`) and stores it in its back-end database.
    3.  The server sends an HTTP response to the user's browser that includes a `Set-Cookie: 1678` header.
    4.  The user's browser stores this cookie in its local cookie file under the entry for `amazon.com`.
    5.  When the user visits Amazon again, the browser finds the cookie for `amazon.com` and includes a `Cookie: 1678` header in its HTTP request.
    6.  The Amazon server receives the request, sees the cookie ID, looks up `1678` in its database, and can now provide a personalized experience based on that user's past activity.
  
  *   **Cookies and Privacy:** Cookies are a powerful mechanism but also a major source of privacy concerns. They permit sites to learn a great deal about user activity. **Third-party cookies** (or tracking cookies) allow a common identity to be tracked across many different websites, creating a detailed profile of a user's browsing habits. This has led to regulations like the EU's GDPR, which require user consent for non-essential cookie usage.
